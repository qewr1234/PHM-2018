# FAB 적용을 가정한 가상 계측 (PHM 2016 CMP)

대회용 모델(`run_cmp.py`, 최종 테스트 MSE 6.29)은 시험 웨이퍼 **앞과 뒤**에 처리된 학습 웨이퍼의 정답을 함께 참고합니다. 공장에서는 불가능한 조건입니다. 공장에서는 이미 처리된 웨이퍼 중 **계측 결과가 도착한 것만** 볼 수 있고, 계측은 연마가 끝나고 한참 뒤에 도착하며, 모든 웨이퍼를 재지도 않습니다.

이 문서는 그 조건을 지키는 두 가지 가상 계측(VM)을 정리합니다. Cheng 외 2007의 이중 단계(dual-phase) VM과 같은 구분입니다.

- **1단계 실시간 VM** (`fab_vm.py`, `fab_sim.py`, `fab_run.py`): 연마 직후(또는 연마 전)에 바로 값을 냅니다. 즉시 판단과 run-to-run 제어용입니다.
- **2단계 확정 VM** (`fab_phase2.py`, `fab_phase2_run.py`): 연마 L시간 뒤에, 그 사이 도착한 앞·뒤 웨이퍼 계측까지 써서 같은 웨이퍼의 값을 다시 냅니다. 로트 판정·SPC용입니다.

이 문서에서 "대회 방식"의 같은 기간 값(6.76 / 6.87)은 이전 3멤버 앙상블(LightGBM + 신경망 + GP, 테스트 6.45 / 검증 6.10, 커밋 3742cdc) 기준입니다. 표 파운데이션 모델을 더한 최종 대회 모델의 같은 기간 값은 따로 계산하지 않았습니다.

실시간 VM은 모든 웨이퍼를 재는 조건(테스트·검증 웨이퍼 정답도 도착하면 다음 예측에 씀)이고, 2단계 VM은 대회 학습 웨이퍼(약 70%)만 재는 조건입니다. 테스트·검증 열은 같은 웨이퍼지만 쓸 수 있는 정답이 다릅니다.

- **공장에서 즉시 쓸 수 있는 실시간 성능은 대회 점수의 약 2배 오차입니다.** 가장 큰 원인은 모델이 아니라 **계측 지연**입니다. 같은 조건 웨이퍼가 3~4분 간격으로 연속 처리되는데, 가장 강한 단서인 "바로 앞 웨이퍼의 실제 연마량"을 지연 때문에 쓸 수 없게 되기 때문입니다.
- 그래도 이 웨이퍼의 센서 기록을 쓰는 LightGBM이 EWMA·칼만보다 오차를 18% 줄였고(15.78 → 12.90), 표 파운데이션 모델 TabICLv2를 칼만 잔차 멤버로 더하면 4.6% 더 줄었습니다(12.90 → 12.31).
- **몇 시간 기다려도 되는 쓰임(로트 판정·SPC)에는 2단계 확정 VM이 대회 수준에 다가갑니다.** 24시간 뒤 확정하면 배포 기간 테스트 / 검증 6.99 / 7.30이고, 대회 방식(6.76 / 6.87)과의 차이는 웨이퍼 짝 부트스트랩 95% 구간이 0을 포함해 뚜렷하지 않습니다. 다만 전체 기간 검증에서는 뚜렷하게 나쁘고(+0.88), 원문을 확인한 대회 방식 최고 발표치 6.36보다 낮다고 볼 근거는 없습니다.
- 90% 예측 구간의 실제 적중률은 89.3%, 구간 반폭은 평균 ±5.8입니다(연마량 약 80 기준 약 7%). TabICLv2를 더하면 89.5%, ±5.6입니다.
- 예측 1건 3.8 ms, 하루 1번 재학습 2.9초(레짐 3개). 대회 파이프라인 전체 학습(약 38분)보다 훨씬 가볍습니다. TabICLv2를 더하면 예측 1건 약 0.1초, 하루 재학습 약 50초(스레드 1개)로 늘지만, 웨이퍼 간격(분 단위)보다 짧아 여전히 실시간으로 쓸 수 있습니다.

## 구성

```
계측 도착 ─▶ VMService.on_metrology()  검증 → 이력 → EWMA·칼만 갱신 → 결합 가중치·예측 구간 갱신
매일 1회  ─▶ VMService.maybe_retrain()  도착한 계측으로 LightGBM 재학습 (선택: TabICLv2 문맥 갱신)
연마 종료 ─▶ VMService.on_wafer()       예측값, 90% 구간, 멤버별 예측, 신뢰 플래그
```

| 구성 요소 | 내용 |
|---|---|
| EWMA (`EWMAPredictor`) | run-to-run 제어의 표준 추정기. 수준 = λ·새 계측 + (1-λ)·이전 수준, λ = 0.5 |
| 칼만 동적 선형 모델 (`KalmanDLM`) | 연마량 = 수준 + b·(드레서 수명 위치, 가공 시간). 수준은 시간에 비례해 흔들리는 랜덤 워크라 오래 안 쟀을수록 불확실성이 커짐. 드레서 교체(사용량 카운터 초기화)를 감지하면 수준의 분산을 키움 |
| 주기 재학습 LightGBM (`OnlineGBM`) | 레짐별, 매일 재학습, gain 상위 120 특징. 입력 = 이 웨이퍼 센서 요약·TS_ 모양 특징 + **예측 당시 도착해 있던** 계측의 이력 특징(최근 편차, 지수가중 평균, 추세, 같은 드레서 수명 평균, 마지막 계측 웨이퍼 대비 상태 차이) + EWMA·칼만 예측 |
| (선택) 표 파운데이션 모델 잔차 멤버 (`OnlineTFM`) | 사전학습된 TabICLv2가 칼만 예측과의 차이를 예측. 매일 도착한 계측으로 문맥만 다시 넣음. 아래 "실시간 VM에 표 파운데이션 모델 멤버 더하기" |
| 온라인 결합 (`OnlineBlend`) | 최근 150개 계측 웨이퍼에서 **그 당시 저장한** 멤버 예측으로 레짐별 NNLS 가중치, 과거 계측 범위로 자름 |
| 예측 구간 (`AdaptiveConformal`) | 적응형 컨포멀 추론(ACI): 계측이 도착해 구간 밖이었는지 확인할 때마다 α ← α + γ(0.1 − 벗어남), γ = 0.005 |
| 신뢰 플래그 | 센서 활성 구간 없음 / 마지막 계측 후 8시간 초과 / 멤버 불일치(표준편차 > 3) / 이력 부족 |

TS_ 모양 특징 목록(정답을 쓰지 않는 가지치기)도 **개발 기간 행만으로** 다시 정했습니다. 배포 기간 데이터는 특징 선택에도 쓰지 않았습니다.

- forecast(연마 전 예측)는 이 웨이퍼 센서 기록 없이 예측하므로 vm보다 20~30% 나쁩니다.

| 100% | 12.90 | 12.90 | 12.90 |

개발 기간 비교(`fab_dev.json`의 `sampling_dev`)에서도 주기 계측이 모든 비율에서 가장 좋았습니다(20%: 주기 14.20, 무작위 15.36, 불확실성 16.89, 멤버 불일치만 23.18, 절반 주기 + 절반 불확실성 18.81).

**예상과 반대였던 점.** 불확실성이 큰 웨이퍼를 골라 재는 방식(Han 외 2025의 분산 기반 동적 표본을 변형)이 가장 나빴습니다. 불확실성이 큰 웨이퍼는 대개 **오래 쉰 뒤 처음 들어온 웨이퍼**였습니다(계측한 웨이퍼의 직전 계측 후 경과 시간 중앙값 13.1시간, 안 잰 웨이퍼 6.4시간). 쉬고 난 첫 웨이퍼는 로트 대표성이 낮아, 그 값으로 뒤따르는 웨이퍼를 보정하면 오히려 틀립니다. 그래서 이 데이터와 이 모델에서는 **"조건별로 N장마다 1장"을 권합니다.** Han 외 2025는 가우시안 프로세스의 예측 분산(입력 공간 거리 포함)을 썼고, 여기서는 칼만 분산(주로 경과 시간)을 썼다는 차이가 있습니다.

### 3. run-to-run: 연마 시간 결정

forecast 예측 f로 연마 시간을 "목표 제거량 / f"로 정하면, Preston 식에 따라 실제 제거량의 상대 오차는 y/f − 1입니다. 배포 기간 1,582장:

| 연마 시간을 정한 방식 | 전수 계측(지연 1시간): RMS 오차 · ±5% 안 비율 | 20% 주기 계측 |
|---|---|---|
| 고정 레시피 (개발 기간 조건별 평균) | 14.6% · 24.5% | 14.6% · 24.5% |
| EWMA (전통적 R2R) | 4.82% · 74.1% | 5.32% · 68.8% |
| 칼만 | 4.82% · 73.5% | 5.36% · 67.8% |
| LightGBM | 5.36% · 67.8% | 6.49% · 57.6% (n = 1,530) |
| **결합 (최종)** | **4.72% · 74.7%** | **5.30% · 68.6%** |

- 계측을 되먹이는 것만으로 제거량 오차가 14.6% → 4.8%로 1/3이 됩니다. 소모품 마모로 연마량이 계속 움직이기 때문입니다.
- 연마 **전** 예측에서는 ML이 EWMA를 거의 못 이깁니다(4.82% → 4.72%). 이 웨이퍼 센서 정보가 없으면 남는 단서는 과거 계측의 추세뿐이고, EWMA가 이미 그것을 잘 씁니다. ML의 가치는 연마 **후** 품질 추정(vm)에서 더 큽니다.

### 4. 신뢰 플래그 (지연 1시간, vm)

|---|---|---|---|
| 멤버 불일치 | 5.1% | 14.59 | 12.81 |
| 마지막 계측 후 8시간 초과 | 12.1% | 11.19 | 13.14 |

멤버 불일치만 실제로 큰 오차를 가려냈습니다. 나머지 두 플래그는 대부분 챔버 그룹 1(연마량이 안정적인 조건) 웨이퍼라 오히려 오차가 작았습니다. 운영에서는 **ACI 구간 폭과 멤버 불일치**를 신뢰도 지표로 쓰고, 나머지 두 플래그는 데이터 품질 알림으로만 쓰는 편이 맞습니다.

## 실시간 VM에 표 파운데이션 모델 멤버 더하기 (TabICLv2)

대회 방식에서 가장 강한 단일 모델이었던 표 파운데이션 모델(TFM)을 실시간 VM에도 네 번째 결합 멤버로 넣었습니다(`fab_vm.OnlineTFM`, 설정 `FINAL_CFG_TFM`). 기본 설정(`FINAL_CFG`)과 그 결과(`fab_results.json`의 `scenarios`)는 그대로 두고 별도 설정으로 비교했습니다.

| 항목 | 내용 |
|---|---|
| 모델 | TabICLv2 회귀 (`tabicl` 2.2.0, 코드·가중치 BSD-3, 가중치 `tabicl-regressor-v2-20260212.ckpt`). 합성 표 데이터로 사전학습된 트랜스포머에 학습 행을 문맥으로 넣어 예측합니다(in-context learning). 사전학습 가중치는 바꾸지 않습니다 |
| 목표 | 실측 − 칼만 예측 (칼만 예측이 없으면 조건 평균). 예측 = 모델 출력 + 같은 칼만 예측. 칼만 예측이 없는 초기 행은 학습에서 뺌 |
| 학습 행·특징·시각 | LightGBM 멤버와 같음: 매일 1번, 그때까지 도착한 계측 웨이퍼, 레짐별. "재학습"은 도착한 계측 행을 문맥으로 다시 넣는 것뿐입니다(kv_cache: 문맥 계산을 재학습 때 한 번 해 두고 웨이퍼마다 한 행만 추론) |
| 입력 열 | 그 재학습의 학습 행만으로 짧은 LightGBM(OnlineGBM과 같은 120 트리)을 돌려 고른 gain 상위 100 열 |
| 설정 | 앙상블 4, 스레드 1, `random_state=0`. 가중치는 `data/cmp2016/tfm_cache/hf/hub`에서만 읽고 내려받지 않습니다(없으면 받는 명령을 알려 주고 멈춤) |

## 2단계(Phase-II) 확정 VM

실시간 VM의 한계는 계측 지연 때문에 **같은 로트에서 함께 처리된 웨이퍼의 실측을 아직 쓸 수 없다**는 데 있습니다. 로트 판정이나 SPC처럼 몇 시간 늦어도 되는 쓰임이라면, 기다렸다가 그 사이 도착한 계측으로 같은 웨이퍼의 값을 다시 내면 됩니다. Cheng 외 2007의 이중 단계 VM에서 새 계측이 도착한 뒤 다시 내는 2단계 값(VM-II)에 해당합니다. 대회 방식은 기다리는 시간에 제한이 없고 모델도 미래 정답으로 학습한 극단입니다.

### 규칙

| 항목 | 설정 |
|---|---|
| 계측 웨이퍼 | 대회 학습 세트 − 큰 이상치 4개 = 1,977장 (전체 2,829장의 약 70%, 데이터셋 자체의 표본 계측). 테스트·검증 848장은 계측하지 않은 웨이퍼로 보고 정답은 채점에만 씀 |
| 계측 도착 | 웨이퍼 j의 정답은 a_j = 연마 종료 + 1시간에 도착 |
| 값을 내는 시각 | 웨이퍼 i의 확정값은 D_i = 연마 종료 + L (L = 1·4·24시간). a_j ≤ D_i 인 계측 정답(j ≠ i)만 씀 → i 뒤에 연마됐어도 D_i 전에 도착했으면 씀(지연 안의 앞보기). L = 1시간은 지연과 같아 앞보기가 없고(앞서 연마된 웨이퍼 정답만 모두 도착), L = 4시간이면 연마 뒤 3시간 동안 처리된 웨이퍼 정답까지 씀 |
| 재학습 | 학습 멤버는 T_k = k × 24시간(6시간 멤버는 6시간)마다 max(D_j, a_j) ≤ T_k 인 계측 웨이퍼로 학습(각 행의 특징은 자기 D_j 시점 기준)하고, T_k < D_i ≤ T_k + 간격인 웨이퍼를 예측 |
| 고르는 것 | 레짐별 RTS 잡음비, 결합 멤버 조합(후보 19개, L = 1시간은 14개), 동결 가중치. 모두 개발 기간 선행 예측(7일 이후이고 max(D_j, a_j) < 30일인 계측 웨이퍼)으로만 고름 |
| 본 결과 (online 결합) | 레짐별 NNLS 가중치를 매일 그때까지 나온 선행 예측으로 다시 맞추고, 그때까지 도착한 정답 범위로 자름. 개발 기간 선택을 빼면 완전 인과 |
| 참고 결합 | 개발 기간 동결(개발 기간에 맞춘 가중치 고정, 배포 기간은 인과) / 전체 기간(미래 정답 사용 → 인과 아님, 낙관적 참고치로만) |
| 대회 비교 기준 | 커밋 3742cdc의 `results.json` 예측 (이전 3멤버 앙상블, 테스트 6.445 / 검증 6.099) |

선행 예측(prequential)은 계측 웨이퍼 j에 대해 같은 규칙으로 D_j에 낸 예측입니다. j의 정답이 도착한 뒤에야 채점할 수 있으므로 결합 가중치와 선택에 인과적으로 쓸 수 있습니다.

### 멤버

- **특징** (L = 24·4시간 605열, 1시간 579열): 정답이 필요 없는 특징(실시간 VM과 같은 센서 요약·TS_ 모양 특징; TS_ 가지치기와 상태 표준화는 개발 기간 행만으로) + D_i 시점에 도착한 정답으로 만든 특징(과거 계측, 지연 안 앞보기 계측, 양쪽 가우스 커널·앞뒤 보간·최근접, 소모품 상태 최근접, 4A↔4B 교차 스테이지, 같은 웨이퍼 다른 스테이지).
- **RTS 평활**: 레짐별 국소 수준 모델을 앞·뒤 두 필터로 고정 지연 평활합니다(15분 넘는 공백은 로트 경계로 보고 점프 잡음을 더함). 학습이 없는 비교 멤버로 1시간 가우스 커널(K1)과 앞뒤 선형 보간(INT)도 둡니다.
- **LightGBM** (학습 행에서만 고른 gain 상위 120 열): 원값(`gbm`), RTS 잔차(`gbm_res`, 시드 3개 평균), 세 레짐 통합 RTS 잔차(`res_pool`, 시드 3개 평균), 6시간마다 재학습하는 잔차(`res_6h`, `res_pool6h`).
- **표 파운데이션 모델 RTS 잔차 멤버** (학습 행에서만 고른 gain 상위 100 열, 레짐별, 앙상블 4): TabDPT 1.3.1(Apache-2.0), TabPFN v2(`ModelVersion.V2` 가중치만, 문맥 = 최근 학습 행 300개), TabICLv2(kv_cache). L = 24·4시간은 셋 다, 1시간은 TabDPT만 돌렸습니다. 가중치는 `data/cmp2016/tfm_cache`에서만 읽습니다.
- **Built with PriorLabs-TabPFN.** TabPFN v2 가중치는 Prior Labs License 1.1(Apache-2.0 + 표기 조건)이라 이 표기를 밝힙니다. TabPFN 2.5 이후 가중치는 비상업 라이선스라 쓰지 않습니다.

- L = 4시간은 테스트 차이 +1.388(95% +0.556 ~ +2.309), 6.36보다 낮을 확률 0.041입니다. L = 1시간은 +3.685(+2.471 ~ +5.029), 확률 0입니다.

정직한 해석:

- **완전 인과인 2단계 VM(24시간)은 비인과 대회 방식에 못 미칩니다.** 테스트 차이는 유의하지 않지만 검증 차이는 유의합니다. 배포 기간만 보면 차이가 작고 테스트·검증 모두 유의하지 않습니다.
- **인과적으로 6.36을 넘는다고 말할 수 없습니다.** 테스트 부트스트랩 구간이 넓어(5.5 ~ 8.9) 설정을 더 바꾸다 보면 한 번쯤 6.36 아래가 나올 수 있지만, 그것은 잡음에 맞춘 선택이고 검증이 반대 방향을 가리킵니다.
- **이득은 표 파운데이션 모델에서 나옵니다.** 24시간 개발 기간 선행 예측으로 TabDPT 단독 6.417, TabPFN v2 단독 6.418이 가장 좋은 LightGBM 멤버(통합 잔차 6.854)보다 좋습니다.
- **1A가 약점입니다.** 24시간 테스트 1A 9.224(4A 5.751, 4B 7.197)이고, online 결합은 1A에서 RTS에만 가중치(1.0)를 둡니다. 대회 방식에서도 1A가 가장 어렵습니다.
- **선택에도 잡음이 있습니다.** 고르지 않은 가장 큰 조합이 고른 조합보다 테스트·검증에서 나았습니다(6.830 / 6.905). 0.3 이하 차이는 잡음으로 봐야 합니다.

### 누설 검사

- `tests/test_fab_phase2.py` (11개, 합성 데이터 540장): 테스트·검증 정답을 엉터리 값으로 바꿔도 특징·모든 멤버·세 결합이 한 자리도 바뀌지 않는지, 컷오프 C 뒤에 도착하는 학습 정답을 바꿔도 D_i ≤ C 인 웨이퍼의 특징·멤버·online·동결 결합이 그대로인지(컷 4곳), 모든 재학습·결합·자르기 범위의 행이 도착 규칙을 지키는지, 특징이 도착한 정답만 쓰는지(L = 0.5·1·24시간)를 확인합니다. 학습 행에 3시간 뒤 행까지 허용하는 식으로 누설을 일부러 넣으면 테스트가 실패하는 것도 확인했습니다.
- 실제 데이터 (L = 24시간, 줄인 설정: LightGBM 150 트리, TabDPT 앙상블 1로 33일까지 재학습, C = 30.5일, `fab_phase2_results.json`의 `leak_check`): 테스트·검증 정답을 바꿔도 모든 멤버·결합의 차이가 0입니다. C 뒤에 도착하는 학습 정답을 바꿔도 D_i ≤ C 인 1,227장에서 모든 인과 멤버와 online·동결 결합의 최대 차이가 0.0이고, 전체 기간 결합만 최대 7.58 바뀝니다(미래 정답을 쓰므로 예상대로).

### 쓰임새

- **FAB에서 쓸 수 있는 이유**: 확정값을 내는 시각 D_i에 실제로 도착해 있는 계측만, 그 시각 전에 학습한 모델과 그때까지의 선행 예측으로 맞춘 가중치만 씁니다. 공장에서 "연마 L시간 뒤 배치 작업"으로 그대로 돌릴 수 있습니다.
- **쓸 곳**: 로트 판정(규격을 벗어난 웨이퍼 보류·재측정 지시), SPC(웨이퍼별 VM 값 관리도), 품질 추적 기록, 그리고 다음 공정이 D_i 이후에 시작한다면 그 공정 조건을 미리 보정하는 피드포워드.
- **쓰면 안 되는 곳: 다음 웨이퍼 R2R 제어.** 같은 조건 웨이퍼가 몇 분 간격으로 이어지므로 D_i 시점에는 뒤 웨이퍼들이 이미 연마를 마쳤습니다. 연마 시간 결정에는 1단계 값(forecast)을 씁니다.

### 한계

- L = 1시간 결과(10.130 / 9.691)는 실시간 VM 기준 시나리오(12.90)와 비교할 수 없습니다. 계측 비율(70% vs 100%)과 값을 내는 시각(연마 종료 + 1시간 vs 연마 종료)이 다릅니다. 쓸 수 있는 정답의 범위(앞서 연마된 웨이퍼 전부)는 실시간 지연 0과 같습니다.
- 개발 기간(7~30일)의 테스트·검증 값에는 개발 기간 선택이 섞여 있습니다(30일까지 도착한 학습 정답으로 골랐음). 엄밀히 앞을 보지 않은 값은 배포 기간 값입니다.
- TabPFN·TabICL 출력은 torch 스레드 수에 따라 조금 달라질 수 있습니다(스레드 2개로 실행).
- 실행 시간 (L 하나, 공유 CPU 4개): LightGBM 멤버 합계 약 33~37 CPU분(스레드 1개), TabDPT 약 9~11분, TabPFN v2 약 25~26분, TabICLv2 약 23~25분(스레드 2개). 결합·선택·채점은 몇 초입니다.

## FAB 관점에서 정리

1. **대회 점수는 공장 실시간 성능이 아닙니다.** 같은 기간 대회 방식 6.8 vs 실시간 12.9(지연 1시간; TabICLv2 멤버를 더해도 12.3). 공개 저장소들도 시간순 분할에서 오차가 크게 늘었습니다(jsw010204-web: MAE 2.80 → 5.28, kamalpraven: 2.58 → 4.38).
2. **계측 지연을 줄이는 것이 모델을 바꾸는 것보다 효과가 큽니다.** 지연 1시간 → 0이면 12.9 → 9.3. 가장 효과가 컸던 모델 개선(표 파운데이션 모델 멤버, 12.9 → 12.3)도 이만큼은 줄이지 못했습니다.
3. **몇 시간 기다려도 되는 쓰임에는 2단계 확정 VM을 씁니다.** 24시간 뒤 확정하면 배포 기간 테스트 / 검증 6.99 / 7.30으로 대회 방식(6.76 / 6.87)과의 차이가 잡음 안이고, 4시간이면 8.28 / 7.74입니다. 로트 판정·SPC·피드포워드에는 쓸 수 있지만 다음 웨이퍼 R2R에는 쓸 수 없습니다. 인과적으로 6.36보다 낮다고는 말할 수 없습니다(24시간 테스트가 6.36보다 낮을 부트스트랩 확률 0.23).
4. **작은 데이터에서는 표 파운데이션 모델이 가장 강한 멤버입니다.** 대회 방식(단일 모델 CV: TabPFN v2 6.49 vs LightGBM 7.01), 실시간 칼만 잔차 멤버(배포 기간 단독: TabICLv2 12.46 vs LightGBM 15.23), 2단계 확정 VM(24시간 개발 기간 선행 예측: TabDPT 6.42 vs 가장 좋은 LightGBM 6.85) 모두에서 그랬습니다. 대신 CPU 추론 비용이 예측 1건 3.8 ms → 약 0.1초로 커집니다.
5. **계측을 줄일 때는 "조건별 N장마다 1장"이 안전합니다.** 20% 계측(5장 중 1장)으로 15.7, 전수 계측 대비 오차 22% 증가로 계측 비용을 80% 줄일 수 있습니다.
6. **R2R 연마 시간 결정에는 EWMA가 이미 강합니다.** 고정 레시피 대비 효과의 대부분은 "계측을 되먹이는 것" 자체에서 나옵니다(RMS 14.6% → EWMA 4.82%, 결합 4.72%, TabICLv2를 더한 결합 4.66%).
7. **불확실성은 적응형 컨포멀로 보장할 수 있습니다.** 지연·표본 조건이 바뀌어도, TabICLv2 멤버를 더해도 90% 목표 적중률이 유지됐습니다.

## 한계 (1단계 실시간 VM)

2단계 확정 VM의 한계는 그 절에 따로 적었습니다.

- 계측 지연은 고정값으로 가정했습니다. 실제로는 계측 장비 대기열에 따라 달라집니다(Ai 외 2011은 확률적 지연을 다룸).
- run-to-run은 "연마량이 연마 시간과 무관하다"는 Preston 가정으로 계산했습니다. 실제 두께 목표·전 공정 두께 데이터는 없습니다.
- 챔버·레시피가 3가지뿐인 65일 데이터입니다. 신규 레시피, 장비 간 이동, 장기 드리프트는 확인하지 못했습니다.
- 대회 모델의 융합 신경망은 실시간 버전에 넣지 않았습니다(매일 재학습 비용). 주 1회 재학습으로 넣는 것은 다음 과제입니다.
- TabICLv2 멤버는 개발 기간 이득이 4B에 몰렸고(1A·4A는 개발 기간에 조금 나빠짐), 배포 기간에서도 1A는 그대로입니다. 지연 4시간 테스트와 forecast 테스트는 조금 나빠졌습니다.
- 이전에 보고한 "과거만 본 조건 8.56"(이전 버전 문서)은 특징만 과거로 제한하고 모델은 미래 학습 웨이퍼까지 포함해 학습한 값이라 완전히 인과적이지 않았습니다. 이 문서의 수치가 그것을 대체합니다.

## 실행

```bash
# 1단계 실시간 VM
python cmp2016/fab_run.py --stage dev           # 개발 기간 설정 비교, 약 14분 → cmp2016/fab_dev.json
python cmp2016/fab_run.py --stage sampling_dev  # 계측 표본 정책 비교, 약 3분 → fab_dev.json 에 추가
python cmp2016/fab_run.py --stage main          # 배포 기간 시나리오 22개, 약 7분 → cmp2016/fab_results.json
python cmp2016/fab_run.py --stage tfm_dev --procs 2           # TabICLv2 멤버 유무 비교(개발 기간) → fab_dev.json 'tfm_dev'
python cmp2016/fab_run.py --stage tfm_main --procs 2 --reuse  # TabICLv2 멤버를 넣은 시나리오 5개 → fab_results.json 'scenarios_tfm'·'r2r_tfm'

# 2단계 확정 VM (L = 24·4·1시간)
python cmp2016/fab_phase2_run.py --stage features --lags 24,4,1                     # 특징, RTS 잡음비(개발 기간)
python cmp2016/fab_phase2_run.py --stage members --lags 24,4,1 --procs 2 --reuse    # LightGBM 멤버
FAB2_TFM_THREADS=2 python cmp2016/fab_phase2_run.py --stage members --lags 24,4,1 --members '' --tfm tabdpt --procs 1 --reuse
FAB2_TFM_THREADS=2 python cmp2016/fab_phase2_run.py --stage members --lags 24,4 --members '' --tfm tabpfn_c300,tabicl --procs 1 --reuse
python cmp2016/fab_phase2_run.py --stage report --lags 24,4,1                       # 결합·선택·채점·부트스트랩 → cmp2016/fab_phase2_results.json (대회 비교에 git 기록의 3742cdc 가 필요)
FAB2_TFM_THREADS=1 python cmp2016/fab_phase2_run.py --stage leak --lags 24 --procs 1  # 실제 데이터 누설 검사 → 같은 파일의 leak_check

python -m pytest tests/test_fab.py tests/test_fab_phase2.py -q   # 누수·지연·검증·표본 비율, 2단계 도착 규칙 테스트
```

- 웨이퍼별 기록은 `data/cmp2016/fab/<시나리오>.parquet`, 2단계 VM의 특징·멤버 캐시와 웨이퍼별 예측은 `data/cmp2016/fab_phase2/`에 저장됩니다(git 제외).
- `--reuse`는 같은 설정·같은 코드로 만든 기록만 다시 씁니다(실시간: `fab_vm.py`·`fab_sim.py`·`cmp_data.py` 해시, 2단계: `fab_phase2.code_key()`). 코드를 고치면 다시 돌립니다.
- TFM 시뮬레이션 하나는 스레드 1개로 16~64분, 메모리는 최대 약 4GB를 관찰했습니다. 메모리가 모자라면 `--procs`를 줄입니다. 표 파운데이션 모델 가중치는 `data/cmp2016/tfm_cache/`에서만 읽습니다(받는 방법은 [`README.md`](README.md)의 실행 절).
